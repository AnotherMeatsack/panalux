# Feature releases and update walkthroughs

Every release must ship authored discovery content, not only a changelog. The animated intro is independent; do not add update walkthroughs to it.

1. Update `RELEASE_NOTES.md` and its bundled copy. List each user-facing change as a bold bullet heading.
2. Author `Sources/PanaLux/Resources/FeatureWalkthrough.json` for the marketing version, with a new revision and steps explaining exactly where and how to use each change. Review every changelog heading in `changelogHeadings`. Implement real UI targets for new features; do not point new features at unrelated existing controls. The current native launcher highlight and embedded real guide targets live in `StudioWindow.swift` and `FeatureWalkthroughView.swift`.
3. The dedicated Hands-On Tour begins with this same authored walkthrough, so new users and replay users receive it too. Keep Quick Reference, menu names and replay instructions consistent. Explicit Next/Done is required; do not silently mark completion on close, Later or restart.
4. Run `python3 Scripts/check_release_walkthrough.py`, Swift regression tests in safe render mode, and visual checks of every target and smallest supported window. Test fresh preferences, prior builds including the same marketing version, interruption/resume, completed relaunch and replay. CI, app packaging and update packaging enforce the content check. The check validates authored coverage; it cannot invent or judge future feature explanations for you.
5. Build separately with a monotonically increasing CFBundleVersion, Developer ID signing and the established notarization policy. Do not rebuild a running bundle. Back up the app/config before local installation. Verify installed walkthrough visibility, highlights, controls and completion persistence.
6. Package with `Scripts/prepare_update.sh`. ZIP and notes use version-plus-build filenames. Use that same build suffix for the DMG and checksums. Never replace an archive URL referenced by a published feed: caches must continue to receive bytes matching that feed's signature.
7. Push reviewed source normally. For a same-version revision, preserve the original version tag and add a build-specific tag at the new commit; explain both in the release notes. Upload and verify new immutable assets first, then replace only the active `appcast.xml` and update release notes. Keep prior archives recoverable and label them as earlier builds. Do not upload local backups, private validation, settings or source snapshots.
8. Download the live latest feed and new public artifacts. Verify version/build, archive URL/length/signature, asset hashes, code signing and equality with the installed executable. Record limitations honestly, including physical hardware tests and CI/toolchain restrictions.
